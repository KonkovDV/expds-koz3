# bot-8 — надёжность и скорость сдачи КОЗ №3

## Вывод в 3 строки
1. По времени запас большой: на площадке прогон шёл 3:11–3:22 (docs/LB_LOG.md, таблица), а сторож срабатывает на 1620-й секунде (30 мин − 180 с). Офлайн-режим, лимит 2 ГБ (архив 538,8 МиБ), лимит 20k объектов и AVX-512 тоже чисты: всё проверено скриптом.
2. Главный риск — не время, а молчаливая потеря ответа. Исключение в геофизике одного участка срывает лидар и оптику на **всех** участках. Сбой финальной постобработки даёт пустой FeatureCollection, а `main.py` при этом возвращает 0. NaN уходит в GeoJSON. У проверки кропа путь к весам считается от cwd. Первые три случая воспроизведены тестами и исправлены в ветке `bot8-reliability`, четвёртый исправлен по коду.
3. `check_submission.py` (PASS/FAIL, код ≠ 0) и воспроизводимая сборка `build_submission.py` готовы и испытаны. Три настоящих архива дают PASS. 12 из 12 испорченных архивов дают FAIL.

- По фазам на площадке времени нет. `scoring.log` не показывает stdout контейнера (LB_LOG.md, абзацы о второй посылке). Протокол фаз печатается в stdout (`watchdog._emit_protocol`, watchdog.py:105). Площадка его не возвращает, поэтому **время каждой фазы на 4090 неизвестно**.

- `main.py:21` жёстко ставит `OMP_NUM_THREADS=8`. Для 4090 это безвредно. Для локальной проверки в общей машине это нарушает правило «2 потока», поэтому чекер привязывает процесс к ядрам через `taskset -c 0,1`.

### 1.2 Память
- Проверено: пик RSS смоука на CPU — 963–975 МиБ (check_base.log / check_rel.log, опрос дерева процессов). На синтетике это занимает 12 весов в памяти плюс маленькие растры.
- Документировано не мной: пик 4,9 ГБ на 48 участках (AGENT_PLAN.md:17). Лимит 96 ГБ ОЗУ и 24 ГБ VRAM этот пик перекрывает с большим запасом. **Рассуждение:** кэш DEM и предвыборка (`DemPrefetch`, pipeline.py:857-859, глубина 2) растут с числом LAS, но ограничены глубиной.
- OOM хоста (SIGKILL) никто не перехватывает. Такой сбой не оставит файла ответа, если до него не было записи (см. 1.5). Единственная запись идёт в конце — это сознательный выбор после посылки 0,06140 (LB_LOG.md, «Первая посылка … Эта запись убрана»).

### 1.3 Офлайн
- AST-граф импортов от `inference/main.py` (25 модулей) не содержит сетевых модулей (requests, urllib, http, socket, huggingface_hub, timm hub …). Проверено скриптом.
- Импорт всех модулей и загрузка 12 весов прошли под `unshare -rn` (сети нет). `HOME`, `TORCH_HOME` и кэши после прогона пусты, то есть ничего не скачивалось. Проверено.
- `infer_nn.Segmenter` создаёт сеть с `encoder_weights=None` (infer_nn.py:58-82), без ImageNet-загрузки.

### 1.4 Архив ≤ 2 ГБ, ≤ 20k объектов, валидность
- Архив `main` весит 538,8 МиБ (564 998 065 Б), в нём 44 файла, распакованный — 541,4 МиБ. Проверено.
- Сборщик репозитория `scripts/build_submission.py` берёт файлы из **рабочего дерева**: `collect` (строки 33-53) включает все `expds/**/*.py`. Проверено: в его архив попал чужой неотслеженный `expds/fastgeom.py` (другого агента), а в архив моего сборщика из коммита — нет. Кроме того, у его архива не фиксированы метки времени, поэтому два прогона дают разный sha256.
- Писатель не проверяет ответ перед записью:
  - `writer.write_geojson` (writer.py:54-67) пишет атомарно (tmp + fsync + replace), но `validate` (70-123) не вызывает;
  - `json.dumps` по умолчанию пишет `NaN`. Проверено тестом: на HEAD в файле `NaN`, такой файл — не строгий JSON;
  - `cap_features` (post) держит ≤ 20 000 объектов, лимит 3000 вершин — в finalize;
  - 100 МБ на записи не проверяются. **Оценка:** при 20 000 объектов по ~700 Б (смоук: 55 704 Б / 80 объектов) это ≈ 14 МБ, риск низкий.

### 1.6 Ускоритель `.so`
- `inference/lib/expds_core.abi3.so`: ELF x86-64, максимум GLIBC_2.14. AVX-512 (`zmm`) нет, ymm-инструкций 8389 (objdump, чекер).
- Сборка для Linux — `x86-64-v3` (scripts/build_rust.py:55-58). `target-cpu=native` задан только для Windows MSVC (.cargo/config.toml).
- На этой машине есть avx512, поэтому `.so`, собранный здесь с `native`, на площадке может упасть с SIGILL. Чекер ловит `zmm`.
