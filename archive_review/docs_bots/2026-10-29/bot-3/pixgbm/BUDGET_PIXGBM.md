## 5. Память и тайлинг
- **[изм]** Пик 706 МБ на самом большом растре (200, 14.13 Мпикс). Минимум 275 МБ (208, 0.13 Мпикс), это база: импорт и модели.
- **[оц]** Наклон ≈31 МБ/Мпикс: (706 − 275) / (14.13 − 0.13). Лимит 2 ГБ будет достигнут при растре ≈55 Мпикс.
- **Тайлинг уже частичный** (код `expds/geo_pixgbm.py`): признаки и predict считаются по окнам CORE = 512 px + PAD_M = 6 м.
  - В памяти целиком остаются растры z, zd (детренд), valid, noise и P-карты.
  - Полный потоковый тайлинг возможен:
    - читать блоками с перекрытием ≥ окна детренда (15 м) + PAD 6 м;
    - писать P-карты в memmap;
    - полигонизировать по блокам со склейкой по границе.
  - Это не сделано, а на объёмах 200–217 и не нужно.
- Процессы шли по одному. При параллельном запуске PIXGBM с лидаром и снимками пик складывается.

## 6. Как уменьшить время (не проверено, кроме пункта о Sf)
1. Отдать predict ≥4–8 потоков: на 14900KS 8 P-ядер, и predict масштабируется (1.83× на 2 потоках) [изм/оц].
2. Только finds (Sf): pred_poly = 45.7 % времени [изм]. Но рекомендован вариант S (обе задачи), а Sf+R3 — отдельный вариант (см. PIXGBM_REPORT.md).
3. Не считать predict вне `valid & ~noise`. Сейчас время уже растёт по валидным пикселям, так что резерв здесь мал.
4. Распараллелить feat по окнам (через процессы) — до −20 % [оц].

### 8.4 Сборка и развёртывание
- `python scripts/pixgbm_compile.py <model_dir> [--treelite] [--target-cpu x86-64]` → `<k>.lleaves.so` + `<k>.lleaves.json` (sha256 модели, num_feature 72, zmm 0). Компиляция: poly 40,0 с, finds 45,1 с; .so 1 133 208 / 1 125 016 Б, «statically linked» (ldd). tl2cgen .so 1 105 752 / 1 130 328 Б.
- Рантайм lleaves: только ctypes + .so, пакеты lleaves/llvmlite НЕ нужны. treelite в рантайме требует пакет tl2cgen.
- Лицензии: lleaves MIT; llvmlite 0.44.0 BSD-2 (+ LLVM Apache-2.0 with LLVM exception); treelite, tl2cgen Apache-2.0.
- Фолбэк: нет .so/.json, другой sha256, ошибка загрузки, неизвестный backend → lightgbm с предупреждением (проверено: `bench2/tiny/md_bad`). Нет poly.txt/finds.txt → предупреждение, все растры «error» → классика.
- ВАЖНО для сборщика (bot-8 `build_submission.py`): model_refs не включает `geophys.pixgbm.model_dir` — poly.txt, finds.txt, *.lleaves.so/json надо добавить в архив вручную; check_submission проверяет zmm только у `inference/lib/expds_core*.so`.

### 8.5 Срок фазы и лестница (код `expds/geo_pixgbm.py`)
- Вызов: `expds/pipeline.py` `geophys_feats()` (стр. 146), блок pixgbm стр. 195–226, вызов `geo_pixgbm.region_feats(reg, cfg, model_dir, guard=guard, status=pst)` стр. 202. guard — TimeGuard из `run()` (стр. 831), передаётся в geophys_feats (стр. 898).
- Срок: `pix_deadline(guard, budget)` = min(guard.t0, старт процесса по psutil) + budget; budget = env PIXGBM_BUDGET_S, иначе `[geophys.pixgbm] budget_s` (300). Ещё ≤ time.monotonic() + guard.left() − guard_reserve_s.
- Перед каждым растром: прогноз = Мпикс(valid & ~noise) × скорость (замеренная в процессе, иначе априорная PRIOR_S_PER_MPX из 8.2 / min(потоки, 4)); не влезает → finds_only (только maggr finds) → classic; ступень липкая на процесс. Внутри prob_map перед каждым окном проверка срока → _Budget → classic_budget. Любое исключение → error → классика этого растра. pipeline сохраняет классику у растров из status["fell"].
- Потоки: EXPDS_PIXGBM_THREADS → EXPDS_THREADS → min(8, cpu_count). Бэкенд: env EXPDS_PIXGBM_BACKEND важнее конфига.
- scripts/geo_predict.py без явного budget ставит 1e9 (офлайн-прогон всех участков одним процессом).
