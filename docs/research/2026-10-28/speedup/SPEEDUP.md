## 2. Что сделано (до/после, равенство, тест)

### 2.1 Rust: LAS → сетка 0,25 м (п. 4 из §7.11) — `rust/expds_fast`, колесо `wheels/expds_fast-0.1.0-cp312-abi3-manylinux_2_17_x86_64.manylinux2014_x86_64.whl`
- Новый отдельный crate (PyO3 0.30 abi3-py312 + numpy 0.30 + rayon, GIL отпускается `py.detach`), лицензия MIT, собран
  `maturin build --release --zig --compatibility manylinux2014 -i python3.12` (290 КБ; проверен импорт из распакованного колеса).
- Функции: `grid_accumulate_raw(buf, rec_len, cls_off, cls_mask, …)` — читает X/Y/Z/класс **прямо из сырых записей куска laspy**
  (без копий полей в Python; форматы 0–5: класс = байт 15 & 0x1F, 6–10: байт 16); `grid_accumulate(X, Y, Z, cls, …)` — то же
  по массивам; `grid_mean(zsum, cnt)` — `float32(zsum/max(cnt,1))`/NaN. Режимы: 0 — класс 2, сумма/число; 1 — без 7/18, сумма/число
  (облако «только земля»); 2 — без 7/18, минимум (для PMF).
- Обёртка `py/las_grid_fast.py`: `accumulate(path, x0, y1, res, W, H, mode)` и `ground_grid(...)` → `g (H, W)` до PMF/заливки.
- **Почему бит-в-бит:** x/y/z считаются как в laspy (`X*scale + offset` в f64, без FMA, z → f32), индексы — усечение как
  `astype(int64)`; суммы — f64 **в порядке точек**, сумма куска с 0.0 прибавляется к накопителю (семантика `zsum += bincount`):
  ячейки делятся на полосы по потокам, каждая полоса проходит точки по порядку; для ячеек «на стыке кусков» (cnt>0 до куска)
  частичная сумма хранится отдельно. Минимум — последовательно, как `np.minimum.at`.
- **Тест** `tests/test_las_grid_fast.py` — **40 passed**: 3 участка (016 PF6, 061 PF3, 101 «всё класс 8»), 3 режима, куски 5 M и
  77 777 (много стыков), сырой путь и путь по массивам — `tobytes()` равны numpy-эталону; `grid_mean` равен побайтно;
  **полный DTM** (Rust-сетка + те же EDT/gauss/valid) == `dtm.build` побайтно (dtm и valid) на всех 3 участках.
- **Замер** (`tools/bench_las_grid2.py`, 105_Вщиж: 16,15 Мточек, 31 Мячеек, LAZ уже в памяти, min из 3, `bench_las_grid_105.jsonl`):

| | numpy (как в `dtm.build`) | Rust, 1 поток | Rust, 2 потока |
|---|---|---|---|
| фильтр + индексы + bincount + среднее | 2,36 с wall / 2,35 CPU-с | 0,93 / 0,91 → **×2,5** | 0,73 / 0,93 → **×3,0** |

  Остаток Rust-пути — в основном первые касания страниц 370 МБ накопителей; на 24-ядерной площадке полосы масштабируются.
  Оценка на площадке при 30 Мпкс (≈77 Мточек, 120 Мячеек): **−3…−5 с** из 20–26 с DTM [оц].
- Подключение: заменить цикл накопления в построении DTM на `las_grid_fast.ground_grid(...)` (остальное без изменений);
  колесо положить в образ рядом с `expds_core` (Dockerfile: `pip install --no-index wheels/expds_fast-*.whl`).
- ⚠️ **Лицензия:** эталон — `dtm.build` EhimenNathan-EXpedition (LICENSE нет). Код **не копировался**: Rust-ядро и обёртка
  написаны заново по семантике numpy-операций; код соперника только импортируется в тестах для сверки. Если сам DTM-путь
  соперника будет в нашей сборке — это отдельный лицензионный риск (решает владелец).

### 2.2 12 каналов рельефа (п. 1 из §7.11): Rust/GPU бит-в-бит — **не делаю, обосновано**
- `relief.channels` — цепочка torch-операций (conv2d с гауссом, avg_pool/bilinear, atan/exp/sin/cos). На CPU torch считает
  свёртки через oneDNN (свой порядок FMA-накоплений), трансцендентные функции — через векторный SLEEF; на GPU — CUDA-libm.
  Rust-порт не может гарантировать совпадение до бита ни с CPU, ни с CUDA-вариантом; «метрически равно» потребовало бы
  перепроверки порогов OOF → нарушает требование задачи. На площадке каналы и так идут на **GPU** (`dev="cuda"`).
- Что проверено и даёт ускорение без изменения битов: **CPU-путь детерминирован по числу потоков** —
  016: sha 29433580… при 1 и 2 потоках; 105_Вщиж (7,75 Мпкс): sha 94dbb96b… при 1 и 2 потоках, 9,41 → 5,99 с wall
  (`relief_threads_105.txt`, `tools/relief_threads_eq.py`). ⇒ запасной CPU-путь в контейнере: `torch.set_num_threads(<все физ. ядра>)`
  (не ограничивать 2), 99 CPU-с → ≈8–12 с wall на 24 ядрах [оц].
- Выброс бота 8 «016: каналы 12 = 5,5 CPU-с» не воспроизводится: 0,33 CPU-с (первый вызов/прогрев).
- Дальше (GPU, бит-в-бит): x9 = x12[[0..7, 11]] (бот 8, п. 2) и `tools/` скрипт-замер на 4090 — в бэклоге.

## 3. Рецепт GPU (RTX 4090, лимит 30 мин, 96 ГБ RAM)
1. **Сабмит: FP32, без TF32, детерминированно** (`torch.backends.cuda.matmul.allow_tf32=False`, `cudnn.allow_tf32=False`,
   `cudnn.benchmark=False`): пороги 0,98–0,9995 чувствительны. AMP/bf16, `channels_last`, `torch.compile` — **только после
   перепорогования на OOF** (ожидаемо ×1,5–2 на forward r18, но не бит-в-бит).
2. Каналы рельефа — на GPU (как сейчас), x9 брать из x12 (бот 8); запасной CPU-путь — все физические ядра (бит-в-бит, §2.2).
3. Чтение: `GDAL_NUM_THREADS=ALL_CPUS` в Dockerfile (контрольные суммы растров равны при 1/2/ALL), read-ahead блоков (§2.4) —
   прячет декодирование за GPU-работой.
4. DTM: колесо `expds_fast` (§2.1) + EDT/процессы по файлам (бот 8).
5. Загрузка моделей: meta-device (по умолчанию в патче) — −1…1,5 с на 8 моделей; `EXPDS_SLOT_ACCUM=1` — включать только после
   замера на 4090 (ожидаемо −~10 % времени сети на мелких окнах; на CPU медленнее).
6. Бюджет контейнера при 30 Мпкс (по §7.11 бота 8, [оц]): CPU-часть 34–44 с → **≈27–37 с** с этим пакетом
   (−3…5 с DTM-сетка, −1…1,5 с модели, −1…3 с writer/круги/окна, read-ahead — перекрытие, не сумма); вместе с § бота 8
   (EDT, тайлинг на GPU, процессы по файлам) — ниже. Запас до 30 мин большой; узкое место — сеть/ансамбль на GPU.
