## 0. Главные структурные гипотезы (по ожидаемому выигрышу)

### S1. «Потолок кандидатов 0,985» — неверное прочтение. Реальный потолок по кандидатам ≈ 0,73, а между ним и 0,315 стоит ранжирование
В `COMMON.md` сказано: «потолок кандидатов (oracle) ~0,985 → теряем на ранжировании, а не на поиске». Это не так.

`scripts/oracle_ceiling.py` и `/workspace/rerank/oracle_ceiling_2026-10-27.json` считают **геометрический** потолок: сам эталон, выданный нашими формами. Это не полнота наших кандидатов.

Полноту кандидатов я посчитал по честному stack: `audit/work/layer_recall.py` → `layer_recall.json`. В таблице «потолок» — доля эталона, у которого есть хоть один кандидат с любой уверенностью; «оставлено» — кандидат выше порога группы; «TP» — после жадного матча.

| класс | эталон (fam) | потолок кандидатов | оставлено | TP |
|---|---|---|---|---|
| курганы повр. | 3547 | 2316 (65 %) | 1191 | 1098 |
| курганы целые | 1457 | 1033 (71 %) | 733 | 711 |
| finds_points | 3069 | 2051 (67 %) | 2051 | 1792 |

Как это читать:
- Если бы идеальный ранкер оставил всех кандидатов, попавших в эталон, и не оставил ни одного ложного, балл был бы ≈ **0,726**. Расчёт — команда python в журнале аудита по числам выше; оценка оптимистичная, потому что один кандидат может накрыть эталоны двух типов разметки.
- Значит, есть две потери одного порядка:
  - **(а) ранжирование.** По курганам из 2316 доступных берём 1098. У sp_focal 1014 оставленных дают 203 TP (stack).
  - **(б) поиск.** Для object_poly, архитектуры и фортификаций потолок 27–42 % — объектов просто нет среди кандидатов.
- Лидеры (0,39–0,62) почти наверняка закрывают (а) хорошим вторым этапом. У нас его нет: `models/kurgan_lgbm.txt` в [models] не подключён.
- **Вывод для стратегии:** перестать считать поиск решённым. Сначала ранкер курганов (S2), затем поиск для op/arch/fort (S4).

### S2. Курганы ae и sp_or: в кандидатах есть, на выдачу не попадают (вес 50 из 100)

По ae и sp_or теряется больше половины кандидатов из потолка. Причины в коде:

- Оценка: перевод +30 % «потолок − оставлено» по ae и sp_or в TP при той же точности даёт ≈ +0,02…0,04 балла. Это экстраполяция, её надо проверить табло.

Метрика сводит класс по всем типам разметки и картам. Один физический объект, размеченный в li и ae (или на серой и цветной карте MagGr, или на нескольких срезах/профилях EtGr), — это несколько эталонов. Каждому нужен свой полигон.

`dup_possible` в `layer_recall.json` — оставленные предсказания, у которых в точке есть ещё один свободный эталон:
- повреждённые: 204 (li 190);
- целые: 67 (ae 63);
- finds: 241;
- EtGr: 76.

Цена:
- **Оракульная копия только туда, где есть второй эталон:** повр +0,016, целые +0,007, finds +0,005, op +0,008. Расчёт — команда в журнале по kept/tp из `stack_arch_base.json`.
- **Слепая копия всех оставленных:** повр −0,0002, целые −0,005, finds −0,008.
- Значит, выигрыш даёт только **предсказание, где есть второй слой**: покрытие растра другого типа плюс классификатор «есть ли там объект на этом слое».

  - Это совпадает с отказом табло 27.10 в `docs/PLAN.md:41`. Дешёвый вариант «×2 с decay» стоит проверить.

- **verify** включён в конфиге (`[verify] enabled = true`), а в `ARCHITECTURE.md` описан как выключенный. Документация расходится.
