# StrataTrace — поиск археологических объектов по лидару, снимкам и геофизике

## 📋 Описание

Решение для КОЗ №3 «Комплексирование» находит на данных участка семь классов археологических объектов:
повреждённые и целые курганы, городища, архитектуру, фортификации, площадные объекты геофизики и находки. Вход —
облака LAS, спутниковые снимки, ортофото, исторические аэрофото и карты магниторазведки, электроразведки и
термографии. Выход — один GeoJSON FeatureCollection в EPSG:3857, только Polygon.

**Архитектура — позднее слияние по типу съёмки.** Каждый тип съёмки обрабатывает своя ветка со своей шкалой
уверенности и своими порогами. Объекты разных типов съёмки не склеиваются: по метрике курган, размеченный и на
лидаре, и на снимке, — два эталона.

| Тип съёмки | Метод |
|---|---|
| Лидар | ЦМР из LAS: класс «земля», ячейка 0,1 м, пустоты — интерполяцией по триангуляции Делоне; облако больше 60 млн ячеек — мозаикой кусков. Курганы — ансамбль десяти сетей U-Net с энкодером ConvNeXt-T и точечной головой CenterNet (карта центров, размер, смещение): по пять фолдов на 5 и на 12 каналах рельефа, логиты усредняются по сетям и по восьми поворотам и отражениям (D8). На участках с LAS ансамбль заменяет курганы сети U-Net ResNet-18. Городища и фортификации — маски U-Net (ResNet-18) на ЦМР 1 м; городища — ещё и правило формы рельефа (обрывистый край поднятой площадки). Канал σ рельефа добавляет курган, если он дальше 12 м от уже найденного |
| Спутник | Городища — маска; курганы — карта центров с фокальной потерей, на участках без лидара ещё и окно 256 м; архитектура — круги. Курган переоценивается классификатором окна 96 px вокруг него |
| Ортофото | Сеть архитектуры, общая со спутником |
| Аэрофото | Маска фортификаций. Уверенный курган лидара копируется в слой аэрофото, если снимок покрывает точку |
| Магниторазведка | Находки — пиксельный бустинг: шесть моделей LightGBM на 60 многомасштабных признаках карты (Гаусс, DoG, LoG, гессиан, градиент, локальные статистики, аналитический сигнал), пики сглаженной карты вероятностей. Маски границ съёмки и шума из `extra/` применяются к находкам. Площадные объекты — детектор аномалий относительно фона |
| Электроразведка | Площадные аномалии по изолиниям и LightGBM; каждый срез и профиль — отдельный слой |
| Термография | Детектор аномалий относительно фона |

После веток идёт постобработка: переоценка кругов архитектуры моделью LightGBM, пороги групп, склейка дублей
одного объекта с перекрывающихся снимков одного типа съёмки, копия кургана другого подкласса, курган — круг 0,5 м
в найденном центре, проверка геометрии и лимиты файла по ТР (не более 20 000 объектов, 3000 вершин у полигона,
100 МБ). Архитектура, площадные объекты и фортификации выдаются диском 0,05 м во внутренней точке найденного
полигона (`[post.micro_disks]`): засчитанный полигон остаётся засчитанным, а прогноз «внутренняя точка в эталоне,
покрытие меньше половины» становится попаданием.

**Подбор порогов.** Все пороги выбраны официальной метрикой на обучающей выборке по кросс-валидации: семья
участков (первое слово названия) целиком уходит в проверочный фолд. По баллу публичной выборки пороги не
подбирались. Одно исключение раскрыто в техническом отчёте (раздел 5.2): для порога серых карт MagGr режим
уверенности на картах площадки оценён по точности и полноте геофизики в журнале площадки.

**Системы координат.** У растра берётся его собственная CRS. `UTM.json` участка нужен, если CRS у растра нет
или она не переводится в EPSG:3857, например безымянная LOCAL_CS. Географическая CRS в `UTM.json` заменяется
зоной UTM по центру участка. Для облака LAS сравниваются CRS из заголовка и из `UTM.json` (политика `vote`).
Если они расходятся, берётся та, в которой рамка облака ложится у меридиана своей зоны. Если подходят обе,
решают растры участка, на которые ложится облако, а при равенстве остаётся `UTM.json`.

**Требования письма организаторов от 17.11.** Маски шума геофизики из `extra/` применяются к находкам. Объекты
одного снимка не сливаются между собой, даже если перекрываются. Сливаются только пересекающиеся объекты одного
класса с разных перекрывающихся снимков одного типа съёмки: это один объект, а его дубль метрика считает ложным
срабатыванием. Слои электроразведки не сливаются никогда. Решение ищет объекты только по входным данным: списков
памятников, имён участков и координат как признака нет.

Подробности метода, метрики и проверки — в [`TECHNICAL_REPORT.md`](TECHNICAL_REPORT.md).

## ⚙️ Требования и установка

### Окружение
- **ОС:** Ubuntu 22.04+ или Windows 11
- **Docker:** образ `pantum/n7q:20261024` (публичный, только окружение; собирается из `Dockerfile`)
- **Python:** 3.12
- **GPU:** CUDA 12.8 (на платформе — RTX 4090); без GPU решение работает на CPU, медленнее

### Установка зависимостей
```bash
pip install torch==2.11.0 torchvision==0.26.0 --index-url https://download.pytorch.org/whl/cu128
```

```bash
pip install -r requirements.txt
```

**Основные библиотеки:**
- `torch==2.11.0`, `segmentation-models-pytorch==0.5.0`, `timm==1.0.30` — сети U-Net и ConvNeXt
- `lightgbm==4.7.0` — бустинг: находки MagGr, электроразведка, переоценка архитектуры
- `rasterio==1.5.2`, `laspy==2.7.0`, `shapely==2.2.0`, `pyproj==3.8.0` — растры, облака точек, геометрия, проекции
- `numpy==2.5.4`, `scipy==1.18.1` — вычисления
- Relief Visualization Toolbox (`rvt-py` 2.2.1, Apache-2.0) — открытость рельефа и SVF; лежит без изменений в
  `inference/cnx/_deps/rvt`
- lleaves 1.3.0 (MIT) и llvmlite 0.44.0 (BSD-2-Clause) — компиляция деревьев LightGBM; едут в архиве в `vendor/`
- _(полный список в `requirements.txt`)_

Rust-ядро ускорения (ЦМР, отмывки, пики) — `inference/lib/expds_core.abi3.so`, исходники — `rust/expds_core`.
Без ядра работают NumPy-версии тех же функций; их равенство проверяет `tests/test_accel.py`.

## 🔧 Описание основных функций

### `expds/pipeline.py`
```python
run(input_dir, output_path, config_path=None, root=None) -> dict
```
Полный прогон: каталог участков → геофизика → лидар → оптика → ConvNeXt-лидар → канал σ → проверка кропа →
постобработка и запись GeoJSON. Возвращает сводку по фазам.

```python
geophys_feats(reg, cfg, guard) -> list[dict]
pixel_chain(reg, cfg, pix, feats, guard) -> list[dict]
```
Детектор геофизики и пиксельная цепочка поверх него: находки MagGr, полигоны EtGr.

### `expds/watchdog.py`
```python
finish(feats, cfg) -> list[dict]
```
Постобработка: переоценка архитектуры, пороги групп, склейка внутри типа съёмки, круги курганов 0,5 м,
микродиски 0,05 м, проверка геометрии. Сторож времени записывает уже найденное за 3 минуты до лимита
платформы в 30 минут.

### `expds/lidar_cnx.py`, `expds/lidar_cnx_head.py`
Загрузка весов ConvNeXt по контракту, подготовка каналов рельефа, тайловый инференс с D8 и декодирование
головы.

### `expds/catalog.py`, `expds/crs.py`
Разбор структуры выборки и имён файлов; выбор CRS и перевод в EPSG:3857.

### `expds/writer.py`
```python
write_geojson(feats, path) -> Path
validate(fc) -> dict
```
Атомарная запись с лимитами ТР и проверка файла по правилам валидатора площадки.

## 🚀 Инструкции по запуску

### Вариант 1: Локальный запуск

#### Обучение модели
Пример — сеть U-Net лидара; полный порядок обучения всех моделей — в разделе «Воспроизведение решения», сети
ConvNeXt — в [`training/lidar_convnext/README.md`](../training/lidar_convnext/README.md).
```bash
python -m expds.train --cache work/cache/li --out models/li_r18_hard2.pt --epochs 30 --batch 16 --val-families СЕМЬЯ
```

#### Инференс
```bash
python inference/main.py ПАПКА_ВЫБОРКИ result.geojson
```

Проверка файла по правилам валидатора площадки:
```bash
python -m expds.writer check result.geojson
```

### Вариант 2: Docker

#### Сборка образа
```bash
docker build -t stratatrace:latest .
```

Образ содержит только окружение. На платформе используется опубликованный образ `pantum/n7q:20261024`,
собранный из того же `Dockerfile`; код и веса подключаются томом.

#### Запуск инференса
```bash
docker run --rm --gpus all -v "$(pwd)":/app -v /путь/к/выборке:/data/input -v "$(pwd)/out":/data/output \
  pantum/n7q:20261024 python inference/main.py /data/input /data/output/result.geojson
```

### Сборка и проверка архива для платформы
Веса в git не хранятся: их берут из архива финальной версии (`models/README.md`). `vendor/` и колесо RVT
скачиваются с PyPI со сверкой sha256:
```bash
python scripts/fetch_thirdparty.py
```

Проверка, что все 178 файлов архива на месте и совпадают со сданными:
```bash
python scripts/verify_archive.py --local
```

Сборка, сверка с манифестом сданного архива и пробный запуск:
```bash
python scripts/build_submission.py --out dist/submission.zip
```

```bash
python scripts/verify_archive.py dist/submission.zip
```

```bash
python scripts/check_submission.py dist/submission.zip --smoke ПАПКА_ВЫБОРКИ
```

Сборка детерминирована: те же файлы и те же веса дают тот же sha256. Если sha256 разошёлся,
`verify_archive.py` назовёт отличающиеся файлы и их источник.

### Финальная версия и попытки финала
Финальная версия — `configs/default.toml` этого репозитория, третья попытка финала (19.11.2026, 22:29 МСК). Из
трёх попыток команды у неё наибольший балл закрытой выборки; сами баллы Оргкомитет сообщает командам
конфиденциально (ТР, п. 8.5), и до публикации Финального рейтинга их здесь нет. От второй попытки финальную
версию отличают две правки постобработки:
1. Микродиски 0,05 м у архитектуры, площадных объектов и фортификаций (`[post.micro_disks]`). Курганы, городища
   и число объектов не меняются.
2. Порог находок серых карт MagGr группы `maggr_pix_grhi` — 0,22 вместо 0,324615.

Обоснование и проверка обеих правок — раздел 5 [`TECHNICAL_REPORT.md`](TECHNICAL_REPORT.md).

### Тесты
```bash
pytest -q
```

Тесты работают на синтетике, данные конкурса им не нужны. Без весов (так идёт CI) пропускаются пересборка
архива, сквозной прогон со всеми весами, загрузка весов U-Net и переоценка архитектуры; если веса лежат в рабочей
копии, выполняются и они. Остальные пропуски — тесты, которым нужны данные конкурса, CUDA или `cv2`.

| Переменная | Что задаёт |
|---|---|
| `EXPDS_REAL_DATA` | папка со стеками предсказаний и эталоном трейна для сверки быстрых путей метрики с эталонными |
| `EXPDS_REAL_FULL=1` | долгий прогон всей цепочки подбора порогов на этих данных |
| `EXPDS_TRAIN_ROOT`, `CNX_PREP_REF` | облако участка 191 обучающей выборки и эталон его подготовки для сверки каналов ConvNeXt |
| `EXPDS_METRIC` | путь к официальной метрике, если не `materials/compute_metrics.py` |
| `EXPDS_KEEP_TMP=1` | не удалять временный каталог сессии pytest |

## 🔍 Воспроизведение решения

Полный процесс от данных до результата:

```bash
# 1. Зависимости
pip install -r requirements.txt
# 2. Эталон обучения из разметки всех участков
python -m expds.gt --root DATA --out work/gt_train.geojson
# 3. U-Net. Пример для лидарной сети; шаг, окно, каналы и классы каждой сети записаны в её чекпойнте (meta)
python -m expds.tiles --root DATA --gt work/gt_train.geojson --markup li --out work/cache/li --res 0.5 --tile 128
python -m expds.train --cache work/cache/li --out models/li_r18_hard2.pt --epochs 30 --batch 16 --val-families СЕМЬЯ
# 4. ConvNeXt-лидар: 10 сетей (c5-in и c12-in, фолды 0–4), GPU; подробно — training/lidar_convnext/README.md
python training/lidar_convnext/make_kernel.py --jobs c5-in:0 --mode prep --slug koz3-cnx-li-prep --owner OWNER --out BUILD
CNX_OUT=work/prep5 python BUILD/koz3-cnx-li-prep/koz3-cnx-li-prep.py          # каналы c5 (LAS из S3)
python training/lidar_convnext/prep12.py --root DATA --out work/relief12        # каналы c12
python training/lidar_convnext/make_dataset12.py work/relief12 work/prep12 --ref work/prep5/cnx_relief
python training/lidar_convnext/make_kernel.py --jobs c5-in:0 --owner OWNER --out BUILD        # так же c5-in:1 … c5-in:4
CNX_GT_FILE=work/gt_train.geojson CNX_PREP_DIR=work/prep5/cnx_relief CNX_OUT=work/c5_f0 \
  python BUILD/koz3-li-cnx-c5-in-0/koz3-li-cnx-c5-in-0.py
python training/lidar_convnext/make_kernel.py --jobs c12-in:0 --owner OWNER --prep-dataset OWNER/koz3-cnx-li-prep12 --out BUILD
CNX_GT_FILE=work/gt_train.geojson CNX_PREP_DIR=work/prep12/cnx_relief CNX_OUT=work/c12_f0 \
  python BUILD/koz3-li-cnx-c12-in-0/koz3-li-cnx-c12-in-0.py
# 5. Пиксельная геофизика
python scripts/pix_clean_train.py sample --root DATA --cache work/pix
python scripts/pix_clean_train.py fit --cache work/pix --out models/pix_clean/ens6/n40r8 --seed 0
python scripts/pix_org_et_oof.py full --cache work/orget --out models/pix_clean/org --seed 0
# 6. Запасной детектор курганов (пики рельефа + LightGBM)
python -m expds.candidates --help
# 7. Пороги групп по кросс-валидации официальной метрикой (OOF-стек предсказаний — work/oof.geojson)
EXPDS_METRIC=materials/compute_metrics.py python -m expds.metric sweep --pred work/oof.geojson --gt work/gt_train.geojson --out work/thresholds.json
# 8. Инференс
python inference/main.py ПАПКА_ВЫБОРКИ result.geojson
```

Параметры обучения каждой сети записаны в её чекпойнте (`meta`), контрольные суммы весов — в
`models/MANIFEST.sha256`. Инференс и архив воспроизводятся побайтно: из git, весов и пакетов PyPI собирается тот
же архив. Обучение воспроизводится по рецепту: GPU и смешанная точность дают другие веса того же рецепта.
Классификатор кропа `sp_crop.pt` обучает `scripts/crop_verify.py`, переоценку архитектуры `rerank_arch_lgbm` —
`scripts/rerank_arch_train.py`; оба учатся на стеке предсказаний вне обучения. Инструменты сборки этого стека
команда передаёт экспертам по запросу.
