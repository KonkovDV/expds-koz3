## 1. Что такое «проход 0,5×» в нашем коде
`_li_with_model(seg, d, …)` с `seg.res = 1.0` вместо 0,5 на **том же** DEM 0,1 м (`d`): `relief_channels(d, 1.0, [lrm_s, lrm_l, slope])` (радиусы LRM в метрах, 8/30 м, не меняются) → `seg.predict` (tile 128, step 96) → кандидаты `candidates.detect(d, cand_p)` (свои work_res 0,5 / relief_radius 15 м, от `seg.res` не зависят) → `sample_probs`. Новый DEM не нужен. Кандидаты те же (проверено: 016 — 784 кандидата × 2 класса при 0,5 и 1,0 м; меняются только вероятности, напр. топ-1 0,265 → 0,182). **Значит, без нового детектора кандидатов проход только переоценивает уже найденные пики** — см. вопросы.

## 2. Замер [изм] — box CPU, `taskset 0,1`, torch 2 потока, best of 2, maxrss 1,05 ГиБ, load avg ≈14 (box перегружен → wall завышен)
Данные: `speedup/sample` LAZ 016_Хога (0,27 Мточек) и 018_Курган_Хога (0,46 Мточек); модель `li_r18_hard2.pt`, загрузка 2,6 с (разово, в проходе 0,5× не нужна — тот же `seg`).

| Участок | DEM 0,1 м | изобр. 0,5 м → 1 м | каналы 1× / 0,5× | predict tta1 1× / 0,5× | predict tta8 1× / 0,5× | li целиком 1× / **0,5×** |
|---|---|---|---|---|---|---|
| 016 | 1,76 с | 704×981 → 352×490 | 0,060 / 0,027 | 1,58 / 0,38 | 14,4 / 3,65 | 1,64 / **0,37** |
| 018 | 2,66 с | 1173×1033 → 586×516 | 0,102 / 0,043 | 2,73 / 0,67 | 25,7 / 7,13 | 2,54 / **0,83** |

- predict 0,5× = **0,25×** от 1× (пикселей в 4 раза меньше); удельно **0,56 с на Мпкс (сетки 0,5 м) CPU-2п tta1**, каналы 1 м — 0,04 с/Мпкс, кандидаты+постобработка — 0,04–0,08 с/LAS (кандидаты можно взять из основного прохода → 0,02 с).
- TTA8 на 0,5× — ×9,5–10,6 (3,65 / 7,13 с) → TTA на 0,5× выключать.
- Вклад в фазу лидара этих же участков (e2e, `speedup/prof/e2e_repo.log` [изм-ист]: 13,1 / 16,3 с): **+2,8 % / +5,1 %**.

## 4. Предложение: как встроить под 1200 с
1. **Где.** Внутри `lidar_feats`, сразу после основного `_li_with_model` на том же `d` (DEM уже в памяти, мозаика и CRS уже разобраны). Альтернатива — в цикле σ после оптики (DEM отдаёт кэш `DemPrefetch`, `EXPDS_DEM_CACHE_GIB=8`), но там при вытеснении кэша — пересборка DEM (+20…40 с), поэтому inline предпочтительнее.
2. **Защита soft-ceiling.** Перед каждым LAS:
   `_soft_ok(guard, "li_half", f"лидар 0,5× {reg.name}", extra_s = soft_need_s("wide_window") + soft_need_s("sigma") + soft_need_s("verify"))`
   — так проход, хотя он идёт раньше, не съедает резерв более ценных поздних фаз (как σ уже резервирует verify). Пропуски — в `guard.soft_skipped` (как у остальных).
3. **Ключ need.** `SOFT_NEED_DEFAULT["li_half"] = 30` с; `[time.soft] li_half = 30`, env `EXPDS_SOFT_NEED_LI_HALF_S`. Плюс динамика: `need_las = max(5, 0.35 × t_main_li_этого_LAS × tta)` — если меньше остатка, пропуск только этого LAS.
4. **Порядок отказа (первым отбрасывается →):** `li_half` → `wide_window` → `sigma` → `verify`, пока бот 2 не покажет Δ на OOF/Эрентуне. Для σ на LB есть +0,0032 (0,350588 → 0,353793), у half-res пока только [оц] OSINT. Если покажет ≥ +0,005 — поставить после `wide_window`.
5. **Конфиг (по умолчанию выключено):**
   ```toml
   [li_half]
   enabled = false
   res = 1.0              # м/пкс; DEM 0,1 м тот же
   tta = 1                # на 0,5× не включать (×10 к времени)
   reuse_dem = true
   reuse_candidates = true   # кандидаты из основного прохода; иначе свой detect
   classes = ["kurgany_tselye", "kurgany_povrezhdennye"]   # остальные классы не выводить
   max_px = 30_000_000    # предел пикселей при 1 м; выше — пропуск LAS
   skip_mosaic = true     # li_mosaic / li_coarse — пропуск в v1
   dedupe_m = 12          # как li_dev: drop_near_kurgans + KEPT_KURGAN_CONF
   group = "li_half"      # свои пороги в thresholds_by_markup.li_half

   [time.soft]
   li_half = 30
   ```
6. **Выход.** Отдельная `threshold_group = "li_half"`, дедуп против уже принятых курганов основного li (по образцу `li_dev`): проход должен добавлять только то, что основной не нашёл или отбросил, иначе дубли бьют по точности.
7. **Память:** 0,5× — это ¼ карты вероятностей основного li; пик RAM не растёт (замер 1,05 ГиБ включает оба прохода).
