## 2. ОТДЕЛЬНО: CRS в UTM.json (запрос бота 1)
**(1) 101/103 в run4.** UTM.json у обоих: `{"utm":"36N","crs":"urn:ogc:def:crs:EPSG::32636"}`. SpOr tif — тоже EPSG:32636. Провал sp_or с CRS **не связан**. Географический UTM.json есть у `008_Герите` (`{"utm":"WGS84","crs":"urn:ogc:def:crs:EPSG::4326"}`), там же растр Or в EPSG:4326 (108386×98570, участок только Or).

**(2) Устойчивость bc5aa15 (до фикса):**
| Потребитель | Откуда CRS | Устойчив? |
|---|---|---|
| sp_dfine | `crs_for = read_utm_json` → `utm_for` возвращает fallback как есть | **Нет.** На реальном Герите: `Scene` 1×1 px (воспроизведено) |
| dfine_aeor (bot-6, в v4) | тот же `S.utm_for` + `read_utm_json` (v4 pipeline 1160–1161, dfine_aeor 590) | **Нет** (тот же путь) |
| gor_gate / gor_dense (bot-5, `bot5-gor-dense-v3`) | `gor_gate._epsg` → `read_utm_json` → 4326 → тайлы GSD 2/4 м в градусах | **Нет** |
| li / li_dev | `pipeline.region_crs` → `build_dem(crs=…)` (UTM.json приоритетнее LAS) | **Нет**: ЦМР из метровых точек помечается как 4326 |
| tiles (обучение) | `read_utm_json` для DEM | **Нет** (тот же случай) |
| sp/or оптика | собственная CRS растра; `raster.open_metric` сам перепроецирует градусы в UTM; UTM.json — только запасной вариант | Да (по коду; e2e на Герите не запускал) |
| запись в 3857 | геометрии переводятся из рабочей CRS | Да, если рабочая CRS верная |

**Фикс — коммит `0876090` в `bot7-candidate-v3fix` (от bc5aa15, не запушен):**
* Одна точка: `catalog.read_utm_json` → `crs.project_region_crs(raw, region_dir)`. Географическую CRS заменяет зона UTM 326xx/327xx по центру участка: берётся первый растр с CRS, затем LAS с CRS, затем растр без CRS с правдоподобными градусами. В журнал пишется WARNING `[crs] <участок>: CRS участка EPSG:4326 географическая — беру UTM по центру участка EPSG:32638 (lon …, lat …)`. Если центр не определить — WARNING, CRS остаётся как есть. Проекционные CRS проходят без изменений и без открытия файлов, поэтому для остальных 209 участков выдача та же. Результат кэшируется (lru_cache).
* Через `read_utm_json` идут все перечисленные потребители (pipeline.region_crs, crs_for sp_dfine/dfine_aeor, gor_gate/gor_dense, tiles, gt, candidates).
* Страховка в `sp_dfine.utm_for`: географический fallback не принимается, зона считается по центру растра (как предлагал бот 9 в §11.2).
* Тест `tests/test_bot7_geographic_utm_json.py`, синтетический участок EPSG:4326 (≈Герите, зона 38N). Проверяет read_utm_json/region_crs (utm_json и vote) = 32638, `gor_gate._epsg` = 32638, Scene ≥400×600 с шагом 0,5 м, центр в 3857 с точностью <2 м, страховку utm_for, юг → 32738, сохранение проекционной CRS, случай без файлов. На bc5aa15 тест падает (`'EPSG:4326' == 'EPSG:32638'`), на фиксе проходит 4/4.
* Реальный Герите: bc5aa15 → Scene **1×1**; v3fix → EPSG:32638, **2070×1883**, ровно как в репро бота 9 (`bot-9/or_fix/repro_crs.log`).
* Полный pytest на v3fix: 464 passed, 9 skipped, 1 failed. Упавший `test_coco_roundtrip::test_grid_cache_roundtrip…` падает и на bc5aa15 (`No module named 'cv2'` в venv) — к фиксу не относится.
* Cherry-pick в v4: `git merge-tree` на bot7-candidate-v4 проходит без конфликтов (сам cherry-pick не делал, v4 не трогал).
