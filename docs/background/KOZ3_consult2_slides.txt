Структура обучающей выборки
●   Данные сгруппированы по археологическим территориям (памятникам).
●   Внутри одной территории могут находиться данные нескольких типов.
●   Данные одной территории можно использовать совместно.
●   Тип данных определяется по условному обозначению в названии папки или файла.
●   Аннотации представлены в формате GeoJSON.
●   Разные модальности могут покрывать территорию не полностью и не совпадать по
    границам покрытия — это допустимая особенность датасета.
    Отличия валидационной выборки
●   Названия территорий анонимизированы: region_XXXX.
●   Эталонная разметка недоступна решению.
●   Для лидарных данных передаются только облака точек LAS.
●   Готовые хилшейды Li в валидационную выборку не входят.
●   Решение должно самостоятельно строить необходимые производные изображения из LAS.
●   Покрытие LAS полностью соответствует покрытию исходных хилшейдов.
●   LAS, хилшейды и разметка географически согласованы и не имеют пространственных
    смещений. Хилшейды строились из LAS методом, описанным в бейзлайне.
●   Результаты обработки LAS относятся к типу данных Li.
Формирование выходного файла
Решение должно сформировать один файл:

GeoJSON / FeatureCollection / EPSG:3857

Каждое предсказание содержит:

 ●   геометрию типа Polygon;
 ●   обязательное поле class_name;
 ●   рекомендуемое поле confidence;
 ●   при необходимости — region_name, markup_type, original_crs, fid.

Допустимы только семь установленных значений class_name.

Неизвестный класс приведёт к ошибке проверки результата.
Формирование выходного файла
Обратите внимание:

 ●   Результаты, полученные по нескольким изображениям одного типа данных, должны
     формировать единую маску объектов.
 ●   Пересекающиеся предсказания необходимо корректно дедуплицировать.
 ●   Объекты, полученные по разным типам данных, не следует объединять только из-за
     пересечения их геометрии.
 ●   Важно сохранить правильный класс, территорию, модальность и географическую привязку
     объекта.

При подготовке результата учитывайте правило сопоставления «один объект эталона — одно
предсказание».
Структура загружаемого решения
Решение загружается в виде ZIP-архива размером не более 2 Гбайт.

Обязательные элементы:

 ●   metadata.json — Docker-образ и команда запуска;
 ●   inference/main.py — единая точка входа;
 ●   модели, веса и конфигурации;
 ●   необходимые зависимости.

В архив нельзя включать данные обучающей или валидационной выборки.

Допускается любой публичный Docker-образ с Docker Hub, поддерживающий Python 3.12 или
выше.
Запуск решения на платформе
1.   Распаковывает архив и проверяет его структуру.
2.   Загружает Docker-образ.
3.   Запускает контейнер без доступа к интернету.
4.   Передаёт путь к входным данным и путь для записи результата.
5.   Запускает inference/main.py.
6.   Проверяет выходной GeoJSON.
7.   Рассчитывает метрику и обновляет рейтинг.

Рекомендуем до отправки воспроизвести этот сценарий локально в Docker.
Ограничения платформы
 ●   Время выполнения решения — не более 30 минут.
 ●   Размер архива — не более 2 Гбайт.
 ●   Среда выполнения не имеет доступа к интернету.
 ●   Текущая конфигурация включает GPU NVIDIA RTX 4090 с 24 Гбайт видеопамяти.
 ●   Контейнеру доступно до 96 Гбайт оперативной памяти.
 ●   Лимит попыток в квалификации — до 3 успешных и до 10 общих запусков в сутки.
 ●   Лимиты обновляются ежедневно в 00:00 по московскому времени.
 ●   При ошибке доступен скачиваемый лог запуска.
 ●   Решению во время запуска доступна полноценная машина указанной на платформе
     конфигурации (1 машина = 1 решение).

* Техническая конфигурация GPU-серверов приводится для планирования решения и при возникших
обстоятельствах может быть заменена организаторами на аналогичную до старта финальных испытаний.
Бейзлайн-решение
Опубликованный бейзлайн демонстрирует полный цикл обработки лидарных данных:

LAS → модель рельефа → хилшейды → тайловый инференс → полигоны → GeoJSON

Особенности примера:

 ●   YOLO-сегментация;
 ●   обработка изображений по тайлам;
 ●   преобразование результата в EPSG:3857;
 ●   дедупликация пересекающихся предсказаний;
 ●   фильтрация слишком маленьких объектов.

Бейзлайн — это отправная точка и пример технической реализации, а не целевой уровень качества.
Метрика конкурса
Weighted Expert F1 — взвешенный F1-score по семи классам:

1.   повреждённые курганы — 30%;
2.   целые курганы — 20%;
3.   городища — 15%;
4.   архитектуры — 10%;
5.   фортификации — 5%;
6.   площадные аномалии object_poly — 10%;
7.   точечные аномалии finds_points — 10%.



 ●   Формулы расчёта приведены в Техническом регламенте.
 ●   Скрипт расчёта опубликован в разделе «Data Science» на платформе.
 ●   Ложное срабатывание учитывается в Precision с коэффициентом 0,5.
 ●   Основной акцент — обнаружить объект, а не точно воспроизвести контур арх. разметки.
Метрика конкурса
Если эталон размечен полигоном:

 ●   перекрытие составляет не менее 50% площади меньшей фигуры;
 ●   внутренняя точка предсказания находится внутри эталонного полигона.

Если эталон размечен точкой:

 ●   расстояние от центроида предсказания до эталонной точки — не более 2 метров.

Дополнительно:

 ●   сопоставление проводится отдельно по каждому классу;
 ●   предсказания проверяются в порядке убывания confidence;
 ●   действует правило one-to-one;
 ●   несопоставленное предсказание считается FP, несопоставленный эталон — FN;
 ●   точность контура не влияет на итоговый балл.
Вспомогательные показатели
Для анализа решения могут рассчитываться:

 ●   Soft Recall;
 ●   среднее отклонение центров;
 ●   отношение FP к TP;
 ●   показатели качества контура;
 ●   результаты отдельно по типам данных;
 ●   результаты по размерным категориям объектов.

Эти показатели не влияют на рейтинг.

Будет добавлено: для успешных запусков участникам станут доступны логи с вспомогательными
метриками, чтобы было проще находить слабые места решения.
Финальная версия исходного кода
Команды, претендующие на призовые места, предоставляют на экспертизу:

 ●   воспроизводимую финальную версию исходного кода;
 ●   описание архитектуры, установки и запуска;
 ●   описание моделей, весов и используемых данных;
 ●   сведения о стороннем коде и лицензиях;
 ●   декларацию об использовании ИИ-инструментов.

Использование ИИ-инструментов разрешено, но команда должна понимать и уметь
объяснить созданный код.

По итогам экспертизы проводится верификация решения. Цель – убедиться в работоспособности
продукта разработки на независимой выборке и добросовестности команды.
