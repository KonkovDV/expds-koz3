## 0. Главное

1. **В открытом доступе уже лежит официальный `compute_metrics.py` КОЗ №3**, бейзлайн организаторов и опись датасета. Их выложила одна из команд КОЗ №3 в публичный репозиторий 18.10. Ваша метрика из ТР должна совпасть с этой версией (`koz3-1.5.0`); сверьте со своей копией с платформы.
2. **Веса классов [факт]:** курганы повреждённые 30, курганы целые 20, городища 15, архитектура 10, `object_poly` 10, `finds_points` 10, фортификация 5. Половина балла — курганы. Фортификация почти ничего не стоит.
3. **`structure.poly` метрика игнорирует [факт].** Его предсказание — пустая работа. Если отдать его под именем `object_poly`, это лишние FP.
4. **Порог выдачи ≈ F/(4−F), а не 1/3 [проверено].** При достижимом F по классу 0,4–0,6 это p ≈ 0,11–0,18. Порог p > 1/3 из вашей архитектуры v2 срезает заметную долю TP.
5. **Попадание центра решает всё [проверено].** Точка, поданная как предсказание, превращается в круг радиусом 2 м и засчитывается для любого полигонального класса, если центр внутри эталона. Это верно даже для городища радиусом 150 м. Контур на балл не влияет.
6. **Возможно, дедупликация между модальностями вредит [проверено механизм, гипотеза по данным].** Разметка в трейне ведётся отдельно по модальностям (`…_Li_курганы…`, `…_Ae_курганы…`). Если один курган размечен и в Li, и в Ae, в эталоне два объекта. Тогда два предсказания дают 2 TP, а одно после дедупликации — 1 TP и 1 FN. Проверьте на трейне до того, как резать дубли.
7. **Признак `(g−i)/(g+i)` из Iskatel-gis бесполезен [факт].** По коду бейзлайна `i = 255 − g`, то есть канал `i` — это инвертированная серая отмывка, а не интенсивность лазера. Признак — линейное преобразование `g`. Уберите его из абляций.
8. **Геофизика в трейне крошечная [факт]:** 13 участков с MagGr, 6 с EtGr, 2 с TerFl. При этом `object_poly` и `finds_points` вместе дают 20 % веса. Класс, который есть в эталоне, но у вас с F1 = 0, штрафуется полным весом. Даже слабый классический детектор лучше нуля.
9. **Призёры прошлых этапов в игре [факт]:** Family, GigaFlex, «Северная звезда», «Орбис» и ещё ~25 финалистов КОЗ №2 зарегистрированы в КОЗ №3. Команды mlart в реестре КОЗ №3 нет (возможно, под другим названием). Все призёры строили решения на YOLO или ансамблях сегментации, отбирали объекты голосованием с упором на precision и настраивали всё под метрику КОЗ №2, где FP стоил столько же, сколько FN. Новая метрика это обесценивает: выигрывает тот, кто первым перестроит пороги под recall.
10. **В метрике есть два бага [проверено]:** объект у границы UTM-зоны (30°, 36°, 42° в. д.) может не засчитаться, а западнее ~9° в. д. допуск для точек сужается до ~1,1 м. Это риск, а не лазейка. Сообщите организаторам.

## 2. Метрика КОЗ №3: как устроена на самом деле

Источник — `compute_metrics.py` версии `koz3-1.5.0` из репозитория Egor-git-cloud. Поведение я проверил, прогнав этот код на синтетических геометриях (таблица 2.2).

### 2.1. Формула [факт]

- **Классы и веса:** `kurgany_povrezhdennye` 30, `kurgany_tselye` 20, `gorodishcha` 15, `arkhitektury` 10, `object_poly` 10, `finds_points` 10, `fortifikatsii` 5.
- `StructurePoly` / `StructPoly` / `StructrPoly` **игнорируются**. Русские синонимы («курганы», «городище» и т. п.) нормализуются. Бейзлайн предупреждает, что имя вне канона отклоняется как `UNKNOWN_CLASS` и сабмит не получает балла.
- **Пулинг:** предсказания и эталон одного класса собираются **со всех регионов сразу**, F1 считается по классу целиком, а не по участку.
- **Precision** = TP / (TP + 0,5·FP); **recall** = TP / (TP + FN); F1 по классу. Итог — взвешенное среднее F1 **только по классам, которые есть в эталоне** (нормировка по решению от 08.10.2026).
- **Сопоставление** жадное, по убыванию `confidence`, один к одному:
  - эталонный полигон засчитывается, если `cov = S(P∩G) / min(S(P), S(G)) ≥ 0,5` **и** `representative_point()` предсказания лежит внутри эталона;
  - эталонная точка засчитывается, если центроид предсказания дальше от неё не более чем на **2,0 м**;
  - предсказание-точка превращается в круг радиусом 2 м.
- **Система координат:** 3857 автоматически пересчитывается в UTM по центроиду каждой геометрии. Пересчёт срабатывает, только если |x| > 1 000 000.
- **Лимиты:** до 20 000 объектов на файл, до 3000 вершин в полигоне, файл до 100 МБ. MultiPolygon оценивается **только по самой большой части**.
- **Справочные метрики** (Boundary IoU, Hausdorff95, PoLiS, разбивка по типам данных и размерам) на итоговый балл не влияют.

### 2.3. Следствия для решения

1. **Оптимальный порог.** F = 2TP / (2TP + 0,5·FP + FN). Кандидат с вероятностью p выгодно выдавать при **p > F/(4−F)**, где F — достижимый F1 класса. Симуляция подтверждает: при F 0,75–0,86 оптимум 0,23–0,26, формула даёт 0,23–0,28. Для ваших реалистичных F 0,4–0,6 порог около 0,11–0,18. Подбирать всё равно на OOF официальным скриптом, но сетку начинать с 0,05, а не с 0,1–0,6.
2. **Выход проще, чем кажется.** Хватает точного центра и одного объекта на экземпляр. Контур можно отдавать грубый, лишь бы его внутренняя точка попадала в объект. Для курганных групп главное — разделить экземпляры: слитый полигон даёт 0 TP.
3. **Приоритеты по весу.** Курганы (50 %) → городища (15 %) → архитектура, `object_poly`, `finds_points` (по 10 %) → фортификация (5 %). Валы и рвы почти не влияют на балл; специалиста под фортификацию стоит делать в последнюю очередь.
4. **Ни одного присутствующего класса с нулём.** Любой класс из эталона с F1 = 0 сохраняет полный вес. Классический поиск пиков для `finds_points` и простой детектор `object_poly` закрывают 20 % веса хотя бы частично.
5. **Дубли эталона между модальностями** — проверьте на трейне (раздел 6).
6. **Не отдавайте MultiPolygon.** Разбивайте его на отдельные объекты, иначе части, кроме самой большой, пропадут.
7. **Ошибка команды yakirill99, которую стоит не повторить:** они считают допуск в единицах 3857 и сопоставляют полигоны по IoU. Официальная метрика работает в UTM и по покрытию меньшей фигуры.

**Смысл карт `Li` [факт, код бейзлайна]:** все четыре построены из LAS по точкам земли.

- `c` — цветная отмывка «Hot to cold» (TerraModeler, 45°/25°), 3 цикла;
- `ch` — та же отмывка, где число циклов = 2·Δz, то есть один цвет соответствует примерно 0,5 м высоты;
- `g` — серая отмывка ArcGIS: азимут 315°, высота 45°, Z = 1;
- `i` = 255 − `g`.

Отсюда два следствия. Корреляция `g` с DTM около 0,05, которую нашли yakirill99, ожидаема: это отмывка, а не рельеф. Поворот как аугментация ломает направление света на `g`, `c`, `ch`.

**Бейзлайн организаторов [факт]:** YOLO-seg по отмывкам, которые он **сам строит из LAS с шагом 0,1 м**. Тайлы 1024 px с перекрытием 30 %, conf 0,25, IoU 0,5, упрощение контура 2 м, дубли отсекаются при IoU 0,95, объекты меньше 1 м² отбрасываются. Модель предсказывает и лишние классы (селища, дороги, ямы, пашни), бейзлайн их выкидывает. На входе ожидаются папки `*_FINAL` или `region_XXXX`, а не `001_Название`, как в трейне. Выход: `class_name`, `region_name`, `sub_region_name`, `markup_type`, `confidence`, `fid`, `crs`.

**Вывод:** не завязывайтесь на имена папок трейна. Проверьте, будут ли готовые карты `Li` в закрытой выборке. Бейзлайн перестал их искать — это сигнал, что их может не быть. Тогда построение отмывок из LAS попадает в бюджет 30 минут.

- **Family:** автор решения, занявшего 1-е место в xView2 (U-Net с сильными энкодерами, Dice + Focal, TTA флипами, пониженные пороги редких классов) **[вывод по имени]**. В КОЗ №2 — 8 сегментационных моделей и голосование «2 из 4». В КОЗ №1 — один YOLO-seg. Desktop на Qt + Leaflet, инференс в отдельном процессе с пулом воркеров.
- **«Орбис» (Владикавказ) и ГЕОИНЖИНИРИНГ (Владикавказ)** — один город и профиль. Связь не подтверждена **[гипотеза]**.

### 4.4. Стеки призёров по документам НТИ [факт]

| Команда | Модели | Важные детали |
|---|---|---|
| Северная звезда, КОЗ 1 | YOLO-seg, один `model.pt` | Дедупликация по IoU, слияние близких полигонов одного класса, GUI на Electron + React |
| Орбис, КОЗ 1 | Ансамбль YOLO | Тайл 1280, перекрытие 128, `--scale-factor 0.25`, `CLASS_THRESHOLDS`, `MIN_AREAS_M2`, папка `changed/` с исправленной разметкой |
| Family, КОЗ 2 | 8 весов: 4 по поверхности + 4 по магнитке | «Ансамблевая сегментация → маска в полигон → порог», Windows-only exe |
| mlart, КОЗ 2 | 3 модели YOLO: `base.pt`, `li.pt`, `maggr.pt` | PyQt6 WebEngine + FastAPI + Leaflet; растеризует LAS; ~30–180 с на 2000² px |
| GigaFlex, КОЗ 2 | 6 весов: 4 доменных (спутник/орто, аэро, ALS-растр, магнитка) + 2 специалиста (`arkhitektury`, `object_poly`) | `oamt_tile_yolo.py`, `infer_semseg.py`, `pipeline_invariants.py`; рекомендованное железо совпадает с платформой (24 ГБ VRAM, 128 ГБ RAM) |

### 4.5. Публичные команды КОЗ №3

**yakirill99/ds-expedition:**
- U-Net ResNet34 с двумя головами (маска и heatmap), сшивка окном Ханна, Дуглас–Пекер, NMS по центрам.
- DTM строят сами из LAS: 26–31 канал рельефа и облака точек; Django-интерфейс; железо RTX 5070 и RTX 3050.
- Слабые места: допуск в единицах 3857, матчинг по IoU, `Stitcher` держит 2K × H × W во float32 (около 2,4 ГБ на 10k²), растровые модальности отложены.

**Egor-git-cloud/ds-expedition:**
- Каркас без собственной модели, адаптер бейзлайна, разбиение по «семействам» участков (Гнёздово → train, Семибратнее → val, Судьбищи → test).
- **Публикация конкурсных материалов в открытом репозитории — вероятное нарушение конфиденциальности.** Это их риск дисквалификации.

## 5. Слепые пятна и швы

### 5.1. У призёров прошлых этапов [вывод]

1. **Настроены под старую метрику.** «2 из 4» у Family и специалисты на precision у GigaFlex оптимальны, когда FP стоит столько же, сколько FN. В КОЗ №3 FP вдвое дешевле и засчитывается попадание центра, так что консервативное голосование срезает recall.
2. **Геофизика — общий ноль.** Электроразведки (карты и профили) и термографии раньше не было ни у кого. Данных на обучение — единицы участков. Преимущества инкумбентов здесь нет.
3. **Сырой LAS.** В КОЗ №2 лидар растеризовали или брали готовые растры. Если в закрытой выборке нет карт `Li`, их пайплайны встанут или потратят бюджет времени на отмывки с шагом 0,1 м.
4. **Специалист под фортификацию — потерянное время:** вес класса 5 из 100.
5. **Чего у них нет [вывод]:** простой детекции центров и разделения курганных групп на экземпляры. YOLO это частично даёт; сегментация с голосованием — нет.

### 5.2. У публичных команд КОЗ №3 [факт]

- Канал `i` понят как интенсивность, а это 255 − `g`. Признак `(g−i)/(g+i)` и «тень × уклон» бессмысленны: у Iskatel-gis и, по наследству, в ваших абляциях.
- Неверная система координат метрики (yakirill99) и не согласованы правила склейки эталона (Egor-git-cloud; его документация признаёт это открытым вопросом).

### 5.3. В метрике и регламенте

| Шов | Что делать |
|---|---|
| Граница UTM-зоны: центроиды эталона и предсказания в разных зонах → промах **[проверено]** | Сообщить организаторам. Себе — проверить, сколько эталонных объектов в трейне лежит ближе 50 м к меридианам 30°, 36°, 42° в. д. |
| Западнее ~8,98° в. д. геометрии не переводятся в UTM; допуск для точек сужается до ~1,1 м; смешанный случай даёт промах **[проверено]** | Сообщить организаторам. Себе — проверить долготы участков |
| MultiPolygon — только самая большая часть **[факт]** | Отдавать только Polygon и Point |
| Класс, которого нет в эталоне, не наказывает за FP **[проверено]** | Не повод выдавать мусор, но и бояться выдачи редких классов незачем |
| Правило склейки эталона между модальностями не опубликовано | Задать вопрос организаторам: решает судьбу дедупликации |
| Образы Docker обязаны быть публичными | Кладите в образ только окружение, без кода и весов, как Nikolove и бейзлайн. Код и веса держите в архиве ≤ 2 ГБ |
| Права на РИД у Фонда НТИ (у всех призёров КОЗ 1–2) **[факт]** | Учитывайте для своих проектов: результат у призёров передаётся фонду |
| Финал: загрузка за 3 дня, 2 успешных запуска; без загрузки берутся 2 лучших публичных (по документам yakirill99 и консультации) | Держите на публичке «страховой» сабмит, близкий к финальному |
| Экспертиза кода и очная верификация «добросовестности» | Не эксплуатировать баги метрики. Чужой код и веса из открытых репо и образов не брать: запрет идентичных продуктов и риск дисквалификации |

### 5.4. В вашей архитектуре v2 — что поправить

| Было | Стало |
|---|---|
| Порог p > 1/3 как старт | Стартовать с p ≈ F/(4−F), то есть 0,1–0,2; сетка от 0,05 |
| `(g−i)/(g+i)`, «тень × уклон» в абляциях | Выбросить |
| Инференс на готовых `Li` по умолчанию | Сначала выяснить наличие `Li` в закрытой выборке; держать запасной путь LAS → отмывка |
| Жёсткая дедупликация между моделями и модальностями | Дедупликация внутри модальности — да; между модальностями — только после проверки дублей эталона |
| `structure.poly` как отдельная голова | Не обучать |
| Специалисты для фортификации (v2) | Понизить приоритет; если делать — для городищ (вес 15) |
| Радиус NMS ≈ радиусу засчитывания [проверить] | Допуск для точек — 2,0 м в UTM; полигоны засчитываются по покрытию меньшей фигуры и внутренней точке, IoU не используется |
| Heatmap-голова как v2 | Поднять в v1 для курганов и `finds_points`: метрика засчитывает именно центры |

## 6. Что сделать на этой неделе

1. Сверить `compute_metrics.py` с платформенной копией: `metric_version` должна быть `koz3-1.5.0`, сверить `config_hash` и наличие `config.py`.
2. На трейне посчитать долю эталонных объектов одного класса, размеченных в двух модальностях одного участка (центры ближе 5 м). Если доля заметная — отключить межмодальную дедупликацию и выдавать предсказания по каждой модальности отдельно с `markup_type`.
3. Написать организаторам на ds_analytics@upgreat.one:
   - как склеивается эталон между модальностями;
   - будут ли карты `Li` в закрытой выборке;
   - баг UTM-зон;
   - порог 1e6 в режиме `auto`;
   - допустимы ли точки как выход для полигональных классов.
4. Проверить долготы участков: попадают ли какие-то западнее 9° в. д. или в пределах 50 м от меридианов 30°, 36°, 42°.
5. Первый сабмит строить как детектор центров: курганы, городища, архитектура — точками или небольшими полигонами вокруг центра. Пороги — от 0,1.
6. Геофизика: классический поиск экстремумов для `finds_points` (допуск 2 м) и простая сегментация `object_poly` по MagGr, EtGr, TerFl. Цель — F1 > 0 по каждому присутствующему классу.
7. Свой Docker-образ публиковать без кода и весов.
